# 設計筆記 2 — thinking 如何延伸 codebase-craft

對應 `0-design-direction.md` 第 8 節開放項第一條，並承接 `1-global-thinking-channel.md`
第 10 節的 **L1 契約**（domain 核心身分＋真接縫＋task 架構位置）。本筆記回答：這些
codebase-craft 的輸出，在 thinking 階段**哪裡產生、怎麼產生、怎麼流下去**。

前提：1.0.0 會把 `2026-06-13_pre-thinking-dynamic-redesign` 的六步流程實作出來；本筆記
設計的是**在那六步之上**延伸 codebase-craft，不是另造流程。

---

## 1. 核心認識：不是加一個 phase，是把既有輸出升成一等產物

六步 redesign **已經在做結構思考**——第三步「多角度蒐證」的常用角度草案就含
`結構 / 演化 / 邊界 / 契約`，第四步「收斂成設計決定」的三格判斷已在產出「放哪 / reuse /
pattern」這類決定。

缺的不是思考動作，是**輸出**：目前「domain 真接縫」和「核心身分」是**散在**結構角度的
事實與零散決定裡，沒有被收成一個**具名、證據標記、可被 implement 消費的一等產物**。

所以 codebase-craft 延伸 ＝ **讓 L1 契約成為 thinking 的具名輸出**，用的是既有的角度＋
三格機制，不新增 phase。

---

## 2. 機制 / 原則分流

| 現行/redesign 做法 | 機制 or 原則 | 處置 |
|---|---|---|
| 六步流程、事實平行/判斷序列、三格判斷、不對稱摩擦 | **原則**（成熟、證據錨定、user 已確認） | **保留** |
| 結構/邊界事實散在角度回報、決定散在第四步 | **機制**（輸出未成形） | **升為一等產物 L1** |
| 深度尺（不確定性 × 爆炸半徑） | **原則** | 保留，但爆炸半徑要含 **codebase 維度**（見第 5 節） |

## 3. research ↔ pre-thinking 的 codebase-craft 分工

codebase-craft 橫跨兩步（呼應 user：好實作先從深度理解問題開始）：

- **research（定義問題）**：這問題**真正要解什麼、涉及哪些、哪些現在不做**。這一步**框住
  接縫的範圍**——沒有 scope，就分不清哪些是本 feature 的真接縫、哪些是別人的地盤。
  （對應 user 第 1 點。）
- **pre-thinking（廣度＋深度）**：從已定義的問題出發，產出 **L1＝核心身分 ＋ 真接縫
  （證據標記）**，以及餵 L2 的演化證據。

分界：research 給「邊界的範圍」，pre-thinking 給「範圍內的真接縫與身分」。

---

## 4. L1 兩件輸出各自在哪產生

### 4.1 domain 核心身分

- **是什麼**：這（feature 範圍內的）系統**本質上是什麼**，一兩行——結構決定要服務的對象。
- **哪裡產生**：research 的問題本質 + pre-thinking 第二步「立假設、框範圍」收斂。第二步把
  research 結論收成明確假設時，順帶逼出「這東西的核心身分是 X」這條**框範圍用**的判斷。
- **可操作性準則（防空話）**：核心身分必須能**裁決一個具體結構決定**。測試：若兩個相反的
  結構選法都「服務」你寫的身分，那身分太空泛，重寫。（同六步「凡感覺可蒙混就換成可查證」
  原則。）

### 4.2 真接縫（real seams）

- **是什麼**：domain 的本質邊界——本 feature 會**坐落其上或創造**的 module/abstraction
  邊界。**粒度地板 ＝ 函式/模組/抽象邊界，不再往下**（見 `0-design-direction` 3.2）。
- **哪裡產生**：第三步的 `結構 / 邊界` 角度蒐**事實**（現有邊界、耦合、既有 pattern）→
  第四步三格判斷收成**具名接縫決定**。接縫不是新機制，是第四步一個**具名的決定類別**。
- **證據標記（關鍵）＋ 逐階累積**：完整證據階是
  **已發生的變動（git history）> 已計畫的變動（plan 的未來 task）> domain 本質分界 > 想像**。
  但**證據沿 pipeline 逐階累積**——pre-thinking 當下只拿得到 **已發生 / domain 本質**
  兩階（或「需外部拍板」）；**「已計畫」這一階要等 planning 分解出 task 後才由 planning
  補上**（見第 7 節）。所以 pre-thinking 產出的接縫先標 已發生/domain本質；planning 之後
  可**加強**同一條接縫到「已計畫」。想像不是證據；pre-thinking 當下標不出任一可查證階的
  接縫不是真接縫（DC-1 cargo-cult，見第 6 節）。
- **feature 範圍限定**：只認本 feature 坐落/創造的接縫，**不重畫整個 project 的架構**
  （防 seam astronomy，見第 6 節）。

---

## 5. 深度尺要含 codebase 維度

六步的深度尺是「不確定性 × 爆炸半徑」。codebase-craft 延伸後，**爆炸半徑要含結構維度**：

- 原本爆炸半徑多指 system/資料/權限的擴散。
- 加一問：**這次改動落在哪條接縫上？動到承重邊界嗎？** 動到核心接縫（很多現有/已計畫
  code 坐落其上）＝爆炸半徑大 → 要深想；只在葉節點加東西 ＝ 小。
- 這讓「要不要深想」也對 codebase 結構敏感，不只對 system 後果敏感。

## 6. 死亡拷問（death cases ＋ 偵測）

| 死法 | 靜默失敗長怎樣 | 偵測/防線 |
|---|---|---|
| **Seam astronomy** | pre-thinking 想畫整個 project 架構，接縫爆量、多數是想像 | 接縫 feature 範圍限定 ＋ 證據標記（想像階被拒）＋ 承接筆記 1 的 consumption 紀律（沒 code 坐落的接縫＝噪音） |
| **核心身分空話** | 身分寫成無法裁決任何決定的口號 | 可操作性準則：兩個相反結構選法都「服務」它 → 太空泛，重寫 |
| **接縫無證據標記** | 看起來在做結構思考、其實在憑感覺畫線（DC-1） | 三格紀律：接縫也要落三格之一（證據已決定 / 自己推導＋寫鏈 / 需外部拍板）；標不出證據階＝不是真接縫 |
| **成熟 repo 沿用爛接縫** | 「跟既有一致」沿用了已腐的邊界 | 沿用 redesign 第四步既有警語：引用既有慣例前先確認它沒爛，是爛的就偏離並記為一個決定 |

## 7. 怎麼流到 implement（接筆記 1）＋ 證據沿 pipeline 逐步累積

責任沿 pipeline 分明，證據**沿 pipeline stage 逐步累積**（注意：這裡的「逐步」指
research→pre-thinking→planning 的**流程階段**，不是證據 rank「已發生>已計畫>domain>想像」的
高低——且累積非按 rank 單調：planning 補的「已計畫」正是 rank 的中間層，見 §4.2）：

- **research**：問題本質、scope（哪些做/不做）。
- **pre-thinking**：核心身分 ＋ 真接縫（標 **已發生 / domain 本質** 階）。核心身分＋接縫是
  **設計決定** → 走 redesign 既有的 **「planning Key Decisions 唯一來源」通道**流到 planning
  （不另造機制）。
- **planning**：把 requirement 依 research＋pre-thinking 分解成 tasks——這一步才產生
  **「已計畫的未來 tasks」**（user 定案 Q3：已計畫未來是 planning 的產物，因為它是上游
  處理的結果，pre-thinking 當下還沒有 task 分解）。planning 於是：
  1. 為每個 task 標「坐落在哪條接縫上」＝ L1 per-task 位置（筆記 1 第 10 節）；
  2. 從 task DAG 反轉出 **L2 反向投影**（誰踩我這塊、要什麼）＝填 index.yaml affects 欄；
  3. 用「已計畫 tasks」**加強**相關接縫的證據階（把 pre-thinking 標的 domain 本質接縫
     升級為「已計畫 task 7/12 會擴充」）。
- **implement**：消費 L1（身分＋接縫，來自 pre-thinking）＋ L2（已計畫投影，來自 planning）
  選 pattern（筆記 1 第 6 節）。

**兩個來源、兩件事，不再混為一談**（修正原稿）：pre-thinking 的**演化角度**蒐的是
**已發生**的變動（歷史上這塊怎麼變）→ 用來**識別接縫是否穩定/真實**；planning 的**task
分解**產的是**已計畫**的變動 → 用來填 **L2 投影**。前者是 pre-thinking 職責、後者是
planning 職責，各歸各階段。**「已計畫」證據只可能來自 planning**，因為 task 分解是
planning 才做的事。
